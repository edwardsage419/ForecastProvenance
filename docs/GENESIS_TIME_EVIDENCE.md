# Genesis External Time Evidence

Version: 0.2 candidate
Status: GEN_001 REVIEW CANDIDATE

## Purpose

Genesis needs two distinct time claims:

1. Deadline evidence: the exact subject existed before a frozen wall clock deadline.
2. Durability evidence: the accepted time evidence bundle was committed into a widely witnessed append only system.

These claims use different mechanisms and are never collapsed into one timestamp.

## Time evidence architecture

Scheme family: FPP_TIME_EVIDENCE_V1

For each consequential subject, such as an IssuanceCyclePlan or IssuanceCycleManifest:

1. Seal the subject and compute its final SHA256.
2. Obtain signed external wall clock receipts that cryptographically bind that exact SHA256.
3. Validate receipt quorum against the frozen deadline.
4. Create an immutable ExternalTimeEvidenceBundle containing the subject reference and raw receipt references.
5. Submit the bundle for OpenTimestamps Bitcoin anchoring.
6. Retain and later upgrade the OpenTimestamps proof until a Bitcoin attestation independently verifies.
7. Create a DurabilityVerificationRecord binding the completed OTS proof, Bitcoin verification output, and original evidence bundle.
8. Obtain wall clock receipt quorum for the DurabilityVerificationRecord before the target outcome information barrier.
9. Final prospective eligibility requires valid original deadline quorum, valid OTS Bitcoin proof, and timely durability completion evidence.

A pending Bitcoin proof preserves a pending state. It cannot produce final prospective eligibility.

## Deadline receipt quorum

Policy ID: DEADLINE_RECEIPT_QUORUM_V1

Version 1 requires at least two valid signed receipts from distinct provider groups.

At least one qualifying receipt must be RFC 3161. A Roughtime receipt may provide protocol diversity after its exact wire protocol version, verifier version, and server root key have passed rehearsal.

Each qualifying receipt must independently satisfy:

```text
receipt_subject_sha256 == subject.content_sha256
verified_receipt_upper_bound <= frozen_deadline
```

A provider group represents one operational trust authority. Multiple endpoints or certificates controlled by the same operator count as one group.

The validator does not average provider times. A receipt either independently qualifies or it does not.

Two qualifying independent provider groups are required. Genesis should freeze at least three provider profiles when practical so that one provider outage need not cancel a cycle.

## RFC 3161 receipt profile

A qualifying RFC 3161 receipt retains raw request and response bytes plus enough trust material for later independent verification.

Required checks include:

1. RFC 3161 structure parses successfully.
2. The signed message imprint exactly matches the subject SHA256 under the frozen hash algorithm.
3. The TSA signature validates.
4. The signing certificate and required chain validate against the frozen provider profile.
5. The TSA certificate is authorized for timestamping under the frozen provider profile.
6. The token policy OID is admitted by the provider profile.
7. The request and response nonce are verified when the provider profile uses a nonce.
8. Certificate chain, CRL or OCSP material required by the retention policy is captured and content addressed at stamping time.
9. A conservative upper time bound can be derived.

The upper bound is:

```text
genTime + declared_accuracy
```

If the token omits accuracy, an externally published provider policy may supply a conservative accuracy bound only when the exact policy document is archived and frozen by hash in the provider profile.

If no defensible accuracy bound exists, the token can be retained as auxiliary evidence but cannot count toward deadline quorum.

## Roughtime receipt profile

A qualifying Roughtime receipt must bind the subject hash into the request nonce.

Version 1 nonce construction:

```text
nonce = SHA512(
    "FPP_ROUGHTIME_V1\x00" ||
    subject_sha256_bytes ||
    client_random_32_bytes
)
```

The client random value is generated by a cryptographically secure random source and retained with the receipt.

Required checks include:

1. Exact protocol version is frozen in the provider profile.
2. Exact server root public key matches the frozen provider profile.
3. Delegation signature validates.
4. Response signature validates.
5. The derived nonce is proven to be included in the signed response tree.
6. The response midpoint is inside the delegation validity interval.
7. The receipt upper bound is computed as midpoint plus radius.
8. The upper bound satisfies the frozen deadline.

Roughtime proves that the signed response was generated after receipt of the nonce. Binding the nonce to the subject SHA256 converts that freshness proof into a subject existence claim under collision and preimage resistance assumptions.

Because Roughtime remains an evolving protocol and Cloudflare currently labels its service beta, Roughtime is not mandatory for Genesis version 1. It becomes quorum eligible only through a frozen provider profile and successful rehearsal.

## GitHub timestamps

GitHub server generated timestamps may be retained as an auxiliary public witness.

They do not count toward DEADLINE_RECEIPT_QUORUM_V1 because the current design does not receive a portable provider signature over the exact subject hash and timestamp that can be independently verified without continued platform trust.

GitHub therefore cannot be the Genesis wall clock trust root.

## OpenTimestamps Bitcoin durability layer

Scheme ID: OTS_BTC_BUNDLE_V1

OpenTimestamps is applied to the canonical ExternalTimeEvidenceBundle and is not used as the precise deadline clock.

The bundle binds:

```text
subject_ref
frozen_deadline
receipt_refs
receipt_provider_profile_refs
quorum_policy_ref
```

The OTS proof must bind the exact bundle SHA256.

Final verification requires a Bitcoin attestation accepted by the frozen verifier contract. Bitcoin block header time is not interpreted as a second level issuance timestamp and does not replace wall clock receipt quorum.

## Durability completion rule

After the OTS proof becomes complete and passes strong Bitcoin verification, create an immutable DurabilityVerificationRecord containing:

```text
external_time_evidence_bundle_ref
ots_proof_ref
bitcoin_block_height
bitcoin_block_hash
bitcoin_header_ref
strong_verification_report_ref
```

The exact DurabilityVerificationRecord must itself obtain DEADLINE_RECEIPT_QUORUM_V1 with:

```text
frozen_deadline = target.outcome_information_barrier
```

If completed OTS evidence cannot be externally receipted before the outcome information barrier, the forecast remains historically recorded but is ineligible for the initial confirmatory prospective cohort.

This conservative rule prevents a post outcome OTS completion from being silently promoted to an initial Genesis confirmatory record.

## Verification modes

Genesis acceptance requires at least one strong OTS verification using a locally controlled Bitcoin Core node. Pruned mode is allowed by the OpenTimestamps client documentation.

Routine operation may use lighter checks for monitoring, but a public explorer or remote API alone cannot create a strong Genesis verification record.

The retained verification report records block height, block hash, relevant header data, verifier version, proof SHA256, bundle SHA256, and verification result.

## Failure semantics

Any of these conditions fails closed for confirmatory prospective status:

1. Fewer than two independent deadline receipt provider groups qualify.
2. No qualifying RFC 3161 provider is present.
3. Receipt subject hash mismatch.
4. Unverifiable provider signature or trust root.
5. Unknown or indefensible receipt accuracy when required for deadline comparison.
6. Receipt upper bound after deadline.
7. OTS proof subject mismatch.
8. OTS proof remains unverifiable.
9. DurabilityVerificationRecord is not externally receipted before the outcome information barrier.
10. Required request, receipt, certificate, revocation, proof, or verification bytes are lost.

Provider outage creates an operational failure or omitted cycle. It does not weaken the quorum requirement.

The selected initial mechanisms must have zero recurring cash cost. A provider that later requires payment is removed or versioned through governance rather than silently substituted.
