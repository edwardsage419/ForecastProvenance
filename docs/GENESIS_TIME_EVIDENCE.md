# Genesis External Time Evidence

Version: 0.4 candidate
Status: GEN_001 REVIEW CANDIDATE

Controlling Roughtime update: D026 and `policy:deadline-receipt-quorum:v3` supersede the earlier v2 quorum, nonce, and provider-pool clauses where they conflict. The general separation between precise wall-clock evidence and Bitcoin durability remains unchanged.

## Purpose

Genesis needs two distinct time claims:

1. Deadline evidence: the exact subject existed before a frozen wall clock deadline.
2. Durability evidence: the accepted time evidence bundle was committed into a widely witnessed append only system.

These claims use different mechanisms and are never collapsed into one timestamp.

## Time evidence architecture

Scheme family: FPP_TIME_EVIDENCE_V1

For each consequential subject, such as an IssuanceCyclePlan or IssuanceCycleManifest:

1. Seal the subject and compute its final SHA256.
2. Obtain signed external wall clock receipts that cryptographically bind that exact SHA256.
3. Validate receipt quorum against the frozen deadline.
4. Create an immutable ExternalTimeEvidenceBundle containing the subject reference and raw receipt references.
5. Submit the bundle for OpenTimestamps Bitcoin anchoring.
6. Retain and later upgrade the OpenTimestamps proof until a Bitcoin attestation independently verifies.
7. Final prospective eligibility requires both a valid wall clock quorum and a valid Bitcoin durability proof.

A pending Bitcoin proof can preserve a pending state. It cannot produce final prospective eligibility.

## Deadline receipt quorum

Policy ID: `policy:deadline-receipt-quorum:v3`

Scheme rule: DEADLINE_RECEIPT_QUORUM_V3

Version 3 requires at least two valid signed Roughtime receipts from an exactly three provider profile pool. The three provider groups must be operationally independent and frozen before Genesis acceptance.

Each qualifying receipt must independently satisfy:

```text
receipt_subject_binding == subject.content_sha256
verified_receipt_upper_bound <= frozen_deadline
```

The validator does not average provider times. A receipt either independently qualifies or it does not.

The threshold is always two. Provider outage never lowers the threshold.

An unlisted provider cannot be substituted after observing a failure.

RFC 3161 receipts may be retained as optional auxiliary evidence. They are not required by the version 3 minimum profile and do not reduce the Roughtime quorum requirement.

GitHub server timestamps remain auxiliary only.

## Provider group independence

A provider group represents one operational trust authority.

Different endpoints or signing keys controlled by the same operational authority remain one provider group.

Shared hosting, HSM, software, network, or upstream time suppliers do not automatically merge provider groups. They become an independence blocker only when retained evidence shows shared timestamp issuance control, shared signing key control, common operational trust authority, or another control dependency that defeats the independent group assumption.

The reviewed independence basis is retained in the qualification evidence package and `RoughtimeQualificationReview`, including the `INDEPENDENCE` and `COMMON_DEPENDENCY` criteria, and is transitively bound into the accepted QualificationDecision. ProviderProfile remains the frozen operational and cryptographic identity object and does not duplicate that review evidence.

## Roughtime receipt profile

A qualifying Roughtime receipt must bind the subject hash into the request nonce.

The current nonce construction is:

```text
nonce = SHA256(
    "FPP_ROUGHTIME_V2\x00" ||
    subject_sha256_bytes ||
    client_random_32_bytes
)
```

The output is exactly 32 bytes. Each provider receives separately generated 32-byte client randomness and therefore a distinct subject-bound nonce.

The client random value is generated by a cryptographically secure random source and retained with the receipt.

Required checks include:

1. The exact server root public key matches the frozen ProviderProfile.
2. The protocol version matches the frozen ProviderProfile.
3. Delegation signature validates.
4. Response signature validates.
5. The derived nonce is proven to be included in the signed response tree.
6. The response midpoint is inside the delegation validity interval.
7. The receipt upper bound is computed as midpoint plus radius.
8. The upper bound satisfies the frozen deadline.
9. The raw request, raw response, client random value, server identity, root key, verifier version, midpoint, radius, and verification result are retained.
10. Any key change requires a new ProviderProfile and accepted manifest change before the changed key can count.

Roughtime proves that the signed response was generated after receipt of the nonce. Binding the nonce to the subject SHA256 converts that freshness proof into a subject existence claim under the cryptographic assumptions of the selected hash functions and signature scheme.

No Roughtime provider becomes admissible from documentation alone. Each final ProviderProfile requires a separately authorized non forecast rehearsal and independent review.

## RFC 3161 auxiliary profile

RFC 3161 engineering remains frozen at checker version 1.3 and report schema 1.2 unless a new concrete correctness or security defect is discovered.

Existing retained FreeTSA, DigiCert, Sectigo ordinary, and Sectigo Qualified rehearsal artifacts remain valid historical non forecast evidence under their recorded status.

An RFC 3161 receipt may be retained as auxiliary evidence when it passes its applicable verification rules.

RFC 3161 is not required by DEADLINE_RECEIPT_QUORUM_V3.

No commercial TSA qualification is required for the selected zero recurring cash cost Genesis minimum profile.

## GitHub timestamps

GitHub server generated timestamps may be retained as an auxiliary public witness.

They do not count toward deadline quorum because the design does not receive a portable provider signature over the exact subject hash and timestamp that can be independently verified without continued platform trust.

GitHub therefore cannot be the Genesis wall clock trust root.

## OpenTimestamps Bitcoin durability layer

Scheme ID: OTS_BTC_BUNDLE_V1

OpenTimestamps is applied to the canonical ExternalTimeEvidenceBundle and is not used as the precise deadline clock.

The bundle binds:

```text
subject_ref
frozen_deadline
receipt_refs
receipt_provider_profile_refs
quorum_policy_ref
```

The OTS proof must bind the exact bundle SHA256.

Final verification requires a Bitcoin attestation accepted by the frozen verifier contract.

Bitcoin block header time is not interpreted as a second level issuance timestamp and does not replace wall clock receipt quorum.

## Durability completion rule

After the OTS proof becomes complete and passes strong Bitcoin verification, create an immutable DurabilityVerificationRecord containing:

```text
external_time_evidence_bundle_ref
ots_proof_ref
bitcoin_block_height
bitcoin_block_hash
bitcoin_header_ref
strong_verification_report_ref
```

The exact DurabilityVerificationRecord must itself obtain DEADLINE_RECEIPT_QUORUM_V3 with:

```text
frozen_deadline = target.outcome_information_barrier
```

If completed OTS evidence cannot obtain qualifying external receipts before the outcome information barrier, the forecast remains historically recorded but is ineligible for the initial confirmatory prospective cohort.

This conservative rule prevents a post outcome OTS completion from being silently promoted to an initial Genesis confirmatory record.

## Verification modes

Genesis acceptance requires at least one strong OTS verification using a locally controlled Bitcoin Core node.

A pruned Bitcoin Core node is acceptable when it satisfies the frozen verifier contract and can independently verify the required proof.

Routine operation may use lighter checks for monitoring. A public explorer or remote API alone cannot create the strong Genesis verification record.

The retained verification report records block height, block hash, relevant header data, verifier version, proof SHA256, bundle SHA256, node version, and verification result.

## Failure semantics

Any of these conditions fails closed for confirmatory prospective status:

1. Fewer than two independent frozen Roughtime provider groups qualify.
2. A receipt comes from a provider outside the frozen three profile pool.
3. Receipt subject binding or derived nonce validation fails.
4. Roughtime delegation or response signature fails.
5. The frozen root key or protocol version does not match the observed provider.
6. The midpoint plus radius upper bound is after the frozen deadline.
7. A provider key changes without a new accepted ProviderProfile and manifest change.
8. Required raw receipt or verification bytes are lost.
9. OTS proof subject mismatch.
10. OTS proof remains permanently unverifiable.
11. DurabilityVerificationRecord completion cannot obtain deadline quorum before the frozen outcome information barrier for the initial confirmatory cohort.

Provider outage creates an operational failure or omitted cycle. It does not weaken the quorum requirement.

## Cost rule

The selected initial mechanisms must have zero recurring cash cost.

The minimum Genesis profile must not require a paid commercial TSA, paid API, hosted database, paid blockchain transaction, or paid verification service.

Existing owner hardware, ordinary internet access, local storage, and the already chosen development subscription are treated as owner supplied environment rather than new project service dependencies.

If any selected provider later requires payment or imposes an unacceptable recurring commitment, that provider becomes ineligible for new cycles until a versioned governance decision admits an alternative. Historical evidence remains preserved.
