# Candidate Freeze Package Specification V1

Specification identifier: `CANDIDATE_FREEZE_PACKAGE_SPECIFICATION_V1`  
Version: `1.1` (completeness clarification draft)
Stage: specification draft; no Candidate Freeze Package is identified or accepted by this document.

**Reading rule.** Paragraphs marked **Normative** define the boundary and review requirements of a future Candidate Freeze Package. Paragraphs marked **Descriptive** explain design intent or current status and cannot add authority, change membership, or override a normative rule. This document does not amend the protocol contracts it references. Where a protocol question arises, the exact applicable TrustedManifest and its admitted contracts govern that question.

**Design basis (descriptive).** This draft implements the R2.3.21 boundary review, R2.3.22 content outline, R2.3.23 semantic review, R2.3.23.1 boundary update, and frozen R2.3.24 drafting plan. This version also addresses R24-01, R24-02, and R24-03 under R2.4-SPEC-COMPLETENESS-CLARIFICATION-001. Repository documents named below retain their existing authority boundaries; the added rules govern package membership, review, and freeze-state description only, without changing protocol authority or historical semantics.

## 1. Purpose and Scope

**Normative.** This specification defines the boundary for reviewing a future Candidate Freeze Package: its identity, artifact classes and inventories, exact references, dependency direction, historical compatibility, and package acceptance criteria. A package review must apply an identified version of this specification to an exactly identified candidate set. Approval of this specification is a separate decision from acceptance of that candidate set.

**Normative.** This specification is a package boundary specification. It is not a protocol trust root, a replacement for `TrustedManifest`, a `ManifestAcceptance`, Genesis authority or authorization, forecast authority, or verification that a package has been frozen. A separately constructed package and separately recorded package decision are required. Genesis `ManifestAcceptance` and explicit Genesis authorization remain later, independent transitions under [Trusted Manifest Contract](TRUSTED_MANIFEST.md) and [Genesis Manifest and Acceptance Procedure](GENESIS_MANIFEST_PROCEDURE.md).

**Normative.** The scope excludes creation of a Genesis Ledger, forecast issuance, production or private keys, live anchors, and runtime-generated authority. Runtime records may be classified and retained as evidence under an applicable contract; their presence does not create prospective status.

**Descriptive.** Current safety state for this draft: Genesis `NOT STARTED`; Forecast Ledger `NOT CREATED`; prospective forecast count `0`; `PRODUCTION_QUALIFIED = NO`; Candidate Freeze `NOT AUTHORIZED`.

## 2. Package Identity

**Normative.** The specification identifier and version above identify this drafting document, not a TrustedManifest or a package manifest. A future candidate review must identify the applicable specification version, candidate package identifier and version, freeze stage, scope, effective candidate selection, and exact bytes reviewed. Its record must distinguish committed source bytes from modified or untracked working-tree bytes. A Git HEAD by itself does not identify uncommitted bytes.

**Normative.** A later package manifest must bind the applicable specification version and the exact member identities. A successor candidate's existence or materialization does not make it effective; effective selection must follow its existing lineage authority. Any change in the meaning of inventory membership or classification, authority boundary, reference model, compatibility rule, or acceptance rule requires a new specification version. Pure editorial changes may preserve the semantic version only if normative meaning is unchanged, while any byte-bound digest must still track the changed bytes. A consequential change in candidate members or dependencies requires renewed candidate review and downstream acceptance treatment.

**Descriptive.** [Genesis candidate lineage](../genesis/candidate/README.md) distinguishes effective selection from successor proposals. [Canonicalization and Identifiers](CANONICALIZATION_AND_IDENTIFIERS.md) defines existing object identity and full content-hash references. This specification does not assign an identity to a package that has not been constructed.

## 3. Authority Model

**Normative.** A package review must identify the following roles separately; one role cannot be inferred from inclusion in another:

| Role | Boundary |
| --- | --- |
| A. Bootstrap Governance Root | Independently supplied, out-of-graph Genesis governance root. A candidate cannot select its own accepted root. |
| B. Trusted Manifest | Content-addressed protocol trust root for its applicable historical state; it binds admitted normative dependencies. This specification does not replace it. |
| C. Trust Core controls | Normative contracts and controls only to the extent exact versions are sealed, admitted, and applicable under the governing manifest. |
| D. Genesis domain definitions | Target, method, schedule, source, resolution, policy, and other Genesis definitions only through their exact admitted versions and scope. |
| E. Verification evidence | Reports, reviews, test results, retained source and qualification evidence support a decision but do not appoint their own authority. |
| F. Implementation artifacts | Schemas, validator sources and builds, runtime bindings, and test artifacts are identified and checked under applicable contracts; their presence alone grants no protocol authority. |
| G. Runtime records | Cycle, forecast, evidence, and validation records are evaluated under historical admitted authority. An origin label or a stored result is not prospective eligibility. |

**Normative.** The package inventory must distinguish Trust Core controls from Genesis domain definitions. The six R2.3 design responsibilities are: `ComponentRoleSet` for permitted component roles and object or schema bindings; `ArtifactBindingPolicy` for exact artifact selection, digest checks, cardinality, and missing or extra artifacts; `RuntimeCompatibilityPolicy` for comparison against frozen runtime requirements; `ValidationResultSemantics` for result interpretation and authenticated input closure; `FailureVocabulary` for closed failure meanings and precedence; and `ProjectionProfile` for versioned field selection and a digest recipe for a specified use. These names describe design boundaries. They do not assert that six sealed objects have been instantiated, admitted by a TrustedManifest, or exercised on the Genesis positive path. A projection digest is not a full-object `content_sha256` identity.

**Normative — C01.** `ValidationResultSemantics` defines interpretation boundaries. A successful interpretation, temporal verification, or retained report does not prove complete confirmatory authority unless the underlying admitted runtime authority and all required checks exist and pass. `UNKNOWN` on a required trust condition cannot become a stronger valid claim. The incomplete positive confirmatory path cannot be declared complete by this specification.

**Normative — C04.** Historical Human Review material does not create Genesis scientific selection authority. Human discretion applies only under an exact, accepted review rule for the applicable historical scope; retained wording alone cannot revive a superseded or dormant selection path.

**Descriptive.** The applicable boundaries are described in [Trusted Manifest Contract](TRUSTED_MANIFEST.md), [Forecast Trust Core Normative Contracts](TRUST_CORE_CONTRACTS.md), and [Genesis Manifest and Acceptance Procedure](GENESIS_MANIFEST_PROCEDURE.md). Designed, implemented, tested, effective, accepted, and authorized are distinct states.

## 4. Artifact Inventory Model

**Normative.** A future package must provide separate Trust Core authority and Genesis normative inventories. Each entry must state its class, role, governing authority, exact identity and version, applicable inclusion rule, and required dependencies. The review must account for required, missing, duplicate, and unexpected members under the applicable contracts; it may not silently convert a partial inventory into a complete one. Package inclusion, reference, or retention does not promote an artifact's authority.

| Class | Package-review treatment |
| --- | --- |
| A. Normative authority | Exact admitted governance, manifest, contract, policy, and domain-definition objects, with their scope and authority source distinguished. A designed object is not presumed admitted. |
| B. Verification evidence | Content-bound reports, independent reviews, retained fixtures, external evidence, and qualification evidence used to substantiate a claim. Evidence is not a trust root. |
| C. Implementation artifacts | Exact validator, schema, source, build, dependency, and test artifacts required by the admitted binding. Implementation is not acceptance. |
| D. Operational artifacts | Runtime records, working inventories, logs, and other operational outputs. Classify by actual origin and governing contract; do not treat them as normative definitions. |

**Normative — C05.** Qualification artifacts may be referenced as Class A admitted profiles and decisions or as Class B supporting evidence according to their actual role. Static qualification outputs do not by themselves establish provider state at every later deadline. Any dynamic historical admission claim requires the applicable pinned verifier and content-closed state evidence at the relevant `as_of_utc`. This specification neither claims the qualification transition complete nor chooses a replacement for its unresolved interface.

**Descriptive.** The existing [qualification firewall](GEN_001_PROVIDER_QUALIFICATION_COMPLEXITY_FIREWALL_V1.md) separates the manifest-bound provider decisions from subsystem evidence and historical state recomputation. This section classifies those materials for package review; it does not qualify a provider.

### 4.1 Review basis and independently derived membership

**Normative.** Before reviewing a package, identify and retain a review basis consisting of: the exact specification bytes and version; the declared claim scope and preparation stage; the effective candidate selection and its exact base/patch lineage under the existing selection authority; the exact governing contract versions for that scope; and the separately declared optional-artifact selections. Identify the source and applicable clause of every requirement. This basis is review metadata, not a new policy object or authority root. Neither the proposed inventory nor an artifact's presence may decide which mandatory requirements apply. A reviewer must not substitute a newer successor proposal for the effective selection.

**Normative.** The following materials are required according to their stated applicability. Package control metadata and payload membership must be distinguished; a physical file may carry several metadata sections without creating a new protocol object or schema.

| Required material | Inclusion rule and role |
| --- | --- |
| Package control metadata | Exact package identifier/version, stage, claim scope, specification identity/digest, review basis, and separate Trust Core and Genesis inventories, plus evidence/implementation/operational inventories. Each entry records classification, admission or proposal status, inclusion reason, governing requirement, exact identity/version, storage or reference mode, and dependencies. This metadata grants no protocol authority. |
| Effective candidate material | Retain the exact selection declaration and base/patch bytes needed to reproduce the selected candidate. Include every active object derived from that lineage, with its actual candidate/admission status. A proposed normative object is not an admitted authority merely because it is inventoried. |
| Applicable controls and domain definitions | Include the exact control, policy, contract, and domain-definition versions required by the selected candidate and declared review scope, following their existing governing bindings. The six design-responsibility names in Section 3 do not require inventing six sealed objects. |
| Verification evidence | Include every report, fixture, retained source/evidence artifact, and review input required by those exact bindings for a claim made by the package, together with the inputs needed to reproduce that claim. A report cannot substitute for retained inputs or required re-execution. |
| Implementation artifacts | Include the exact schema, validator/source/build, dependency, test, and runtime artifacts required by the applicable ValidatorContract and supporting implementation/test/runtime bindings. If those bindings are still only proposed, retain their exact design basis and unresolved obligations; do not claim they have been instantiated or exercised. |
| Operational artifacts | Include operational records or logs only when an applicable contract requires them to support a claim in the declared scope. Actual origin and role remain separate from prospective eligibility. |
| Dependency and unresolved-obligation accounting | Account for every consequential dependency derived under Section 4.2, including independently supplied authority inputs, permitted external references, and future obligations outside the current claim scope. An absent artifact cannot be counted as present, admitted, or verified. |

**Normative.** Optional materials are limited to supplementary explanatory reviews, diagnostics/logs, additional verification examples or fixtures, and historical/superseded design references that are not required by the applicable bindings. Each selected optional artifact must have an exact identity/digest, a stated inclusion reason and class, and an explicit limitation on the claims it supports. Its selection is fixed in the review basis before the final membership comparison. An omitted optional item creates no missing-required-member finding. An artifact needed for any asserted claim is required for that claim and cannot be relabeled optional.

**Normative.** Exclude private-key material and other material prohibited by the applicable contracts; bytes without a determinable identity/digest; and unselected artifacts presented as active candidate dependencies. Dormant or superseded HumanReviewPolicy material may appear only as an explicitly selected historical/design reference, never as Genesis v1 instantiated/admitted authority, a required current authority dependency, or a ManifestAcceptance prerequisite. Successor proposals may likewise be retained as optional references without becoming effective. Final package review/acceptance decisions and the later freeze checkpoint remain separately retained downstream records, not members of the candidate payload they identify. They must not create self-reference or become the authority for their own inputs. Exclusion from a package does not authorize deletion of retained historical material.

### 4.2 Expected-membership derivation and dependency references

**Normative.** An independent reviewer must derive membership from the review basis and the rules above, then compare it with the proposed inventory:

1. Reproduce the effective candidate from the exact selection declaration and base/patch bytes. Use the complete active object set as the candidate-membership roots, preserving the distinction between Trust Core controls and domain definitions; obtain additional applicable control/binding roots from their identified governing contracts. Do not use the proposed inventory as the expected root set.
2. Follow the consequential dependency edges defined by those exact contracts to a fixed point. For each artifact, derive its required role, cardinality, version, and permitted storage/reference mode from the applicable clause. Follow explicit binding and retention requirements, not every explanatory prose link. Include the required evidence and implementation inputs for each asserted claim.
3. Unless an existing governing contract requires independent external supply or expressly permits external retention/reference, retain required dependency bytes in the package payload. For a permitted external dependency, record its exact reference or full raw-byte digest, stable locator, source, retention requirement, and the contract clause permitting that mode. Independently obtain and verify the retained bytes for the review. An external BootstrapGovernanceRoot remains an independent trust input even when a copy is retained; a package cannot select its accepted root.
4. Derive the required payload set and required external-reference set separately. Add only the exact optional artifacts selected in the review basis. Expected payload membership is the union of the derived required payload set and that fixed optional set, after applying the exclusions above. The enclosing package manifest/inventory metadata is checked separately and byte-bound by the downstream review record; it does not contain a reference to its own final digest.
5. Require exact equality between the derived sets and their inventory representations. Check every required dependency, missing or unexpected entry, duplicate identity, conflicting version, and cardinality. Additional unaccounted files inside the identified payload are unexpected artifacts; a subset selected by the preparer is not a substitute for complete payload enumeration. Store the derivation and comparison as review evidence.

**Normative.** A future Genesis dependency whose bytes do not yet exist may be recorded only as an unresolved future obligation when its governing design contract places it outside the current claim scope. Such an obligation is not a fulfilled reference or a package member, and remains blocking for any later claim that requires it. Missing requirements inside the current scope, unknown inclusion/cardinality rules, an unspecified governing binding, or inaccessible required external bytes make the corresponding criterion fail or remain UNKNOWN; the reviewer cannot complete the set by personal interpretation. A declared scope cannot remove a requirement that its applicable contracts impose. These package rules do not instantiate a Genesis object or change the dependencies of Genesis v1.

## 5. Reference and Dependency Model

**Normative.** Every consequential object reference in a future package must identify the exact object by `object_id` and full `content_sha256` where its governing contract requires that pair. The governing version must be explicit or unambiguously fixed by the exact referenced object. Raw evidence and implementation bytes require a stable locator and a full digest under their applicable binding. A display name, shortened hash, Git HEAD alone, or semantic ID alone is insufficient to identify reviewed bytes.

**Normative.** Dependency direction is from the candidate package to this applicable specification version and its exact members; from a member to its already identified governing dependencies; and from a later review decision to the exact candidate and evidence basis it reviews. References must be acyclic. An object, report, candidate, or acceptance decision cannot provide its own authority by referring back to itself or to evidence it later creates. Evidence may substantiate a review but cannot become the authority that admits itself. A package review must check exact-reference closure and separately assess semantic completeness; closure alone does not prove completeness.

**Normative.** Where qualification evidence is involved, the review must preserve the distinction between static manifest-bound outputs and dynamic historical state admission. It must identify the exact applicable verifier and retained evidence basis without treating an isolated validation result as proof that every consequential claim path consumes that result.

**Descriptive.** [Canonicalization and Identifiers](CANONICALIZATION_AND_IDENTIFIERS.md) defines full identity and reference rules. [Trusted Manifest Contract](TRUSTED_MANIFEST.md) supplies the trust-root direction. This document adds no hash algorithm, canonicalization rule, or self-contained admission mechanism.

## 6. Compatibility Model

**Normative.** Historical verification must select the manifest, schema, parser, policy, validator, and digest interpretation applicable to the historical object or cycle, through that state’s governing authority. Retained historical bytes and hashes remain immutable. A successor version may govern later material but cannot silently reinterpret or rewrite earlier objects. The package review must record the exact versions and retained evidence needed to reproduce its compatibility claim.

**Normative.** A weaker historical validator cannot be used as a fallback to assert Genesis completeness or prospective authority. A `ProjectionProfile` digest must be interpreted under its exact profile and use; it cannot be recast as a full content identity or rehashed under a successor meaning. Compatibility of a runtime or locally reconstructed record does not prove semantic completeness of the entire system.

**Normative — C06.** Reconstruction of the cycles supplied to a validator does not prove reconstruction of the complete mandatory-cycle universe. A completeness claim also depends on the applicable historical target set, official retained schedule artifacts, and schedule policy, including accounting for missing mandatory cycles and enforced routing through the authoritative path. This specification does not claim those implementation paths complete.

**Descriptive.** [Trusted Manifest Contract](TRUSTED_MANIFEST.md) preserves historical manifest selection; [Genesis Issuance Schedule Policy](GENESIS_SCHEDULE_POLICY.md) defines mandatory-cycle coverage; [Forecast Trust Core Normative Contracts](TRUST_CORE_CONTRACTS.md) separates historical validation from current verifiability. These existing contracts govern their own semantics.

## 7. Acceptance Model

**Normative.** Six stages remain distinct: specification approval; Candidate Freeze Preparation; package acceptance or rejection; Candidate Frozen; Genesis ManifestAcceptance; and separate Genesis authorization. Approval of this specification does not approve a package or authorize preparation or freezing. Preparation or materialization does not accept or freeze a package. Package acceptance is a review decision and does not itself establish Candidate Frozen. Candidate Frozen records only the immutable package and accepted claim scope under Section 7.3; it does not establish Genesis ManifestAcceptance, protocol admission, operational readiness, qualification, or Genesis authorization. Genesis ManifestAcceptance remains governed by its existing policy, evidence, authority, and signature requirements. Separate explicit Genesis authorization remains required after independent final validation and readiness closure; successful final validation alone does not authorize Genesis.

**Normative.** A future package acceptance record must identify the exact candidate and applicable specification version, the exact evidence basis, an explicit `ACCEPT` or `REJECT` decision, unresolved and blocking findings, and its governing review authority. A rejected candidate cannot be treated as accepted; a consequential correction requires a new candidate or renewed review as its governing contract requires. This section defines review criteria only; it does not create that record or a Candidate Freeze Package.

**Normative.** C01 (confirmatory runtime authority), C05 (qualification transition and historical admission interface), and C06 (mandatory-cycle universe reconstruction and enforced routing) remain implementation-completeness blockers until independently resolved and verified. A package review must state the affected scope and cannot report implementation-complete acceptance while these findings remain open. C04’s historical Human Review limit must also be retained. No decision under this section resolves any of those findings by wording alone.

### 7.1 Executable review criteria

**Normative.** Retain a criterion-by-criterion review record that binds the exact candidate/control metadata, specification bytes/version, review basis, evidence digests, methods and applicable contract clauses, observed comparisons/results, findings, and reviewer/decision authority provenance. The evidence required by each method must be independently obtainable. For executable checks, retain the exact command or entrypoint and implementation/runtime identity, inputs, and observed result. For document checks, retain the exact clauses, compared identities/text, and the reason for the conclusion. A narrative assertion of completeness is insufficient.

| Criterion | Evidence | Validation method | PASS condition; FAIL condition |
| --- | --- | --- | --- |
| RC01 Identity and applicability | Specification/control metadata bytes, exact review basis, and candidate-selection/lineage bytes | Check identifiers, versions, digests, stage, scope, and reproduce the effective selection under its existing selection rule | PASS: one exact, consistent basis identifies all reviewed bytes and applicable versions. FAIL: mismatch, unauthorized selection, or claims that uncommitted bytes are identified by HEAD alone. |
| RC02 Expected membership | Governing inclusion/binding clauses, reproduced active candidate, dependency derivation, fixed optional selections, inventories, and complete payload enumeration | Apply Section 4.2 independently; compare required/optional/external sets, exclusions, duplicates, versions, and cardinalities | PASS: exact set equality and complete accounting. FAIL: missing, extra, duplicate/conflicting, prohibited, or required-as-optional artifact; unsupported exclusion or storage mode. |
| RC03 Artifact identity and classification | Retained member/dependency bytes, full identities/digests, governing role/class/admission status, and inclusion reasons | Verify identities/seals under the applicable existing contract; compare classification and asserted role against that contract | PASS: every entry has matching bytes and supported class/role/status/reason. FAIL: wrong bytes/digest, ambiguous identity, proposed-as-admitted authority, or presence/origin/hash treated as authority. |
| RC04 Reference and authority direction | Exact consequential-reference graph, governing contracts, and independently supplied authority-input provenance | Match complete references and versions; check closure and acyclicity; trace each claimed authority to its existing source | PASS: all required edges resolve and authority is independently sourced. FAIL: self-selection, authority substitution, circular admission, projection-as-full-identity, or missing required closure. |
| RC05 Evidence and implementation binding | Exact applicable ValidatorContract and supporting bindings, retained evidence/fixture/report inputs, implementation/runtime bytes, and observed results | Perform the validations or re-execution required by those exact contracts; compare persisted and reproduced results where required | PASS: every check needed for the declared claim is reproducible and passes under the exact binding. FAIL: substituted binding/runtime/input, result mismatch, report-only self-verification, or unsupported positive implementation/operational claim. |
| RC06 Historical compatibility | Exact historical manifests/contracts, retained historical bytes/hashes, and the version/interpretation mapping for any compatibility claim | Check that each historical artifact retains its governing versions and original interpretation; run replay only when required by that historical contract | PASS: successor rules do not reinterpret or rewrite prior objects, reports, or conclusions. FAIL: successor reinterpretation, rewritten history, or weaker historical validation used to assert stronger current authority. |
| RC07 Claim scope and deferred findings | Explicit claim scope; C01/C04/C05/C06 disposition; exact contracts and independent closure evidence for any claimed resolution | Apply Section 7.2; compare every package claim with its demonstrated evidence and all applicable blocking conditions | PASS: scope is supported and every blocking condition for that scope is resolved; out-of-scope deferred limits remain disclosed. FAIL: wording-only closure, unjustified scope reduction, or completeness/readiness/qualification claim with an applicable open blocker. |
| RC08 Decision authority and record reproducibility | Existing project review/governance authorization or accepted review rule supplied independently of the candidate, exact reviewer/decision identity, RC01-RC07 evidence/results, and proposed decision fields | Verify the source, scope, and requirements of that existing authorization; independently reproduce prior checks and compare the proposed decision with their aggregation | PASS: authority already permits the stated package-review decision and all applicable criteria pass. FAIL: self-appointed/undocumented authority, candidate-supplied authorization treated as self-validating, contradictory record, or ACCEPT with an applicable failed criterion. |
| RC09 Candidate Frozen checkpoint (freeze-stage check only) | Exact accepted package and acceptance record, independently sourced explicit freeze instruction, retained bytes/digests and independent reproduction | Verify the checkpoint prerequisites in Section 7.3 after acceptance and confirm their separate recording; compare the accepted and retained package identities and claim scope | PASS: every checkpoint condition is demonstrated and separately recorded. FAIL: acceptance/preparation used as the freeze instruction, changed bytes, unsupported authority/scope, missing retention, or any unmet checkpoint condition. |

**Normative.** RC01 through RC04 and RC06 through RC08 apply to every package acceptance review. RC05 applies to the implementation/evidence claims and checks required by the exact governing contracts for the declared scope. RC09 is a later freeze-stage check and cannot be inferred from acceptance-review PASS. Record applicability with its governing clause; a reviewer cannot waive a required check by choosing a label or omitting its evidence. Missing evidence or an unresolved governing rule is UNKNOWN rather than PASS. Any applicable FAIL or UNKNOWN prevents ACCEPT for the declared scope and prevents a positive freeze determination. An informational review may record findings without appointing a decision authority or asserting package acceptance.

**Normative.** Complete RC01-RC08 against the exact candidate, prior evidence, and independently supplied existing authorization before finalizing acceptance. RC08 checks proposed decision fields and the prior results; a finalized acceptance record is not an input that authorizes itself or a required predecessor of its own criterion evidence. Retain the acceptance record downstream of those checks. Later freeze checks consume that record separately; no later record is retroactively made an input to the acceptance it reviews.

### 7.2 Acceptance scope and deferred findings

**Normative.** A design-boundary-only package review may assess exact candidate/design material without claiming that uninstantiated interfaces are admitted or implemented. It may record ACCEPT only when all criteria applicable to that scope pass and C01/C05/C06, future Genesis dependencies, and other limitations are explicitly retained as unresolved where applicable. Such acceptance covers only that named design scope; it is not implementation-complete acceptance, operational readiness, provider qualification, Genesis readiness, or permission to omit a required member. Any requirement actually needed by that design scope remains blocking.

**Normative.** A review asserting implementation completeness or a stronger operational/qualification claim must supply the exact retained independent validation evidence required by its existing governing contracts and demonstrate resolution of every applicable blocker. C01/C05/C06 cannot be marked closed through this specification, a design-only ACCEPT, a package hash, or a freeze checkpoint. If closure is not demonstrated, those claims cannot receive ACCEPT. Scope labels do not alter forecast, resolution, cohort, qualification, validation, or Genesis rules.

**Normative.** The governing reviewer/decision authority must be identified through an existing project review/governance authorization or accepted review rule supplied independently of the candidate, with exact retained source bytes/reference and the authorized action/scope. Neither this specification nor a package record appoints that authority. If no applicable existing authorization can be demonstrated, report the authority requirement as UNKNOWN and do not issue an authoritative package acceptance or freeze declaration. This requirement does not create a new governance layer or substitute HumanReviewPolicy for Genesis acceptance authority.

### 7.3 Separate Candidate Frozen checkpoint

**Normative.** Candidate Frozen describes an exact retained package within its accepted review scope. It is established only when all of the following are independently demonstrated and a separate checkpoint record is retained after package acceptance:

1. The package was separately constructed, exactly identified, and received a retained ACCEPT decision under the applicable specification version and independently demonstrated existing review authority.
2. The accepted scope is explicit, all applicable acceptance criteria passed, and no open finding blocks freezing that scope. Deferred limitations remain attached to the scope; a design-only frozen package cannot be represented as implementation-complete or production-ready.
3. A separate explicit instruction to freeze that exact package and scope is supplied from the existing project governance/review context, with independently verifiable authority provenance already permitting that action. Neither specification approval nor package acceptance supplies or implies this instruction. This specification does not appoint a freeze authority; absent such existing authorization, Candidate Frozen cannot be asserted.
4. An independent checkpoint comparison confirms that the package control metadata, payload, permitted external references, and exact specification/review-basis bytes are the same as those bound by acceptance. Expected membership is reproducible under Section 4.2. No added, removed, substituted, or consequentially changed artifact is carried across acceptance.
5. The required package bytes, independently supplied authority inputs where applicable, external retained bytes, and reproduction evidence are preserved under their existing retention requirements with exact identities/digests and usable locators. Retention and access are demonstrated, not merely promised.
6. The separate checkpoint record binds the exact package identity/control-metadata digest, acceptance record, explicit freeze instruction and its existing authority source, accepted scope and deferred limits, and independent identity/membership/retention checks. Its checks are prior retained evidence or inline observations, never a reference to the checkpoint's own final digest. It is a downstream audit record of that limited state, not a new protocol trust root or admission object, and is not retroactively inserted into the accepted candidate payload.

**Normative.** Package acceptance is necessary but not sufficient for Candidate Frozen. Preparation, assembly, materialization, test PASS, review PASS, specification approval, acceptance, or a digest alone never establishes that state. Candidate Frozen is not Genesis ManifestAcceptance or Genesis authorization and grants no forecast issuance, production qualification, or live-anchor permission. The later Genesis transitions remain governed by the exact existing contracts and separate authorization.

**Normative.** A consequential change in the accepted package/specification/review basis produces a new candidate and requires renewed acceptance and a separate freeze checkpoint for the new bytes. It cannot inherit Candidate Frozen from the predecessor. Retain the predecessor package and records unchanged; their historical identity and scope are not rewritten.

No preparation, package acceptance, freeze instruction, checkpoint, or Genesis transition is executed by this document.
